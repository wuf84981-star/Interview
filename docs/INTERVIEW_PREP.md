# 面试拷问准备

> 面试官原话：「请务必理解让自己让 AI 写的代码，面试会针对代码细节展开，会一行行过代码。」

## 一、先看清考核意图

| 面试官说的话            | 真实考核点                                |
| ----------------- | ------------------------------------ |
| 「不能依赖现有 agent 框架」 | 你知不知道 Agent 循环的本质是什么，还是只会调 LangGraph |
| 「一行行过代码」          | 你能否解释**为什么这么写**，而不只是「代码能跑」           |
| 「AI 写的代码要理解」      | 承认用了 AI 没问题，但不能出现「这段是它生成的，我不知道为什么」   |
| 「觉得太难不要勉强」        | 筛掉只是把需求丢给 AI 复制粘贴的人                  |

**一句话策略**：主动交代哪些是 AI 辅助生成、你做了哪些取舍和修改，比被问穿要好。诚实 + 有判断力，本身就是加分项。

## 二、八个「为什么」—— 必须答得出

这八个问题覆盖了全部设计决策。答不出任何一个，就说明这个项目不是你的。

### 1. 为什么不用 OpenAI 原生 function calling？

原生 `tools` 参数确实更省事、模型更不容易出错。但题目明确要求「自行实现 LLM 输出的解析逻辑」，用原生方案等于把核心决策与解析交给厂商。

代价是格式稳定性差——所以我在 `parser.py` 做了四层降级，在 `runtime.py` 加了 1 次修复重试。

**加分回答**：原生 function calling 底层也是把 JSON Schema 塞进 prompt、再解析模型返回的 JSON，只是这层封装被厂商拿走了。自己实现一遍才知道坑在哪。

### 2. 解析器为什么要四层降级？

````
原样 json.loads
  → 失败：剥离 markdown 代码围栏（```json ... ```）
  → 失败：括号平衡扫描，从文本里抠出 JSON 对象
  → 全失败：判 invalid，交给主循环重试
````

括号平衡扫描是最关键的一层。有些模型会输出「好的，我来算一下：{...} 以上就是结果」这种带前后废话的内容。扫描时要正确跳过**字符串内部**的 `{` `}` 和转义字符——因为 `final_answer` 里可能包含代码片段，比如用户问 JSON 格式，答案里就有花括号。

### 3. 解析失败为什么只重试 1 次？

因为 `MAX_STEPS=5` 是整轮的预算。重试会消耗步数，重试多次就把调工具的机会挤掉了。重试 1 次仍失败，说明模型这次就是不听格式，继续重试性价比极低，不如降级为原文返回，并告诉用户「模型输出格式异常」。

### 4. 工具结果为什么要写进 session 又标 `visible=False`？

这是两件不同的事：

- **写进 session**：模型下一步要看到工具返回了什么，否则循环无法推进。
- **`visible=False`**：前端只渲染给人看的内容，不该把原始 JSON 和中间的协议文本暴露出来。

所以 `Message` 有两个字段：`content`（模型协议原文，给 LLM 看）和 `text`（人话，给前端看）。这是「同一份数据，两种消费方」的设计。

### 5. context 为什么每轮压缩、不每步压缩？

压缩时机选在 `run_turn` 开头、进入循环之前。因为：

- 一轮之内的消息（用户提问 + 若干工具往返）是**当前任务的完整上下文**，压掉任何一条都可能导致模型丢失关键信息。
- 轮与轮之间才是天然边界——上一轮已经结束了，它的细节可以粗粒度保留。

这也回答了题目「memory 的召回时机」：`build_context()` 每步都重新组装一次，所以上一步的工具结果下一步立刻可见，不存在缓存过期问题。

### 6. 为什么用机械摘要而不是让 LLM 总结？

让 LLM 总结要多一次模型调用——延迟翻倍、成本翻倍，而且失败还要处理。题目也说「基础的压缩即可，复杂的压缩不用在这里实现」。

机械摘要的做法：按消息类型生成固定句式（`用户: ...` / `助手调用 todo(...)` / `工具 weather 成功: ...`），超出 600 字从**尾部**截断（保留最近的，丢最早的，因为最近的更相关）。

**如果被追问「这样会丢语义」**：对，这是明确的取舍。升级方向是用 LLM 做增量摘要，代价是每轮多一次调用。

### 7. 保留最近 8 条是怎么定的？

要覆盖最近一轮的完整工具往返。最坏情况一轮下来是：`user → assistant(调工具) → tool(结果) → assistant(调下一个工具) → tool → assistant(最终答案)` = 6 条。留 8 条有冗余，但不会多到让压缩失效。

### 8. 内存存储，重启就没了，为什么不落库？

题目要求是「多个窗口独立、可以随时接着聊」——这在单进程内完全满足。落库要额外处理序列化、并发写、schema 迁移，与「只实现题目要求功能」冲突。

**这是刻意的取舍，不是偷懒**，README 里写了。如果被问「生产环境怎么办」，答：换成 Redis（带 TTL）或 SQLite，`SessionStore` 的接口已经是 `create/get/list/delete`，替换实现不影响上层。

## 三、逐文件高危追问

### `agent/runtime.py`（190 行，最可能被重点过）

| 追问                                         | 答法                                                      |
| ------------------------------------------ | ------------------------------------------------------- |
| 主循环为什么用 async 生成器而不是普通函数？                  | 要一边执行一边把思考/工具调用推给前端。生成器 `yield` 事件，API 层转成 SSE，不需要等整轮跑完 |
| 为什么是 `for step in range(1, max_steps + 1)` | 步数是**硬预算**，不是 while True。防止模型陷入工具循环把 token 烧光           |
| LLM 调用失败为什么 `return` 而工具失败不 `return`？      | LLM 挂了这一轮彻底没法继续；工具失败可以回灌错误让模型自己修正，循环应该继续                |
| 轮次用尽为什么还给个答复？                              | 直接报错体验太差。给兜底话术 + 保留历史，用户说「继续」能接着做                       |
| `parse_failures` 计数为什么不清零？                 | 一轮内累计，重试额度是整轮的，不是每步的                                    |

### `agent/context.py`（96 行）

| 追问                                           | 答法                                                                              |
| -------------------------------------------- | ------------------------------------------------------------------------------- |
| `compressed_upto` 这个游标的作用？                   | 标记「前 N 条已经压进摘要了」，避免重复压缩，也不用真的删消息（保留原始数据便于调试）                                    |
| 为什么 `role="tool"` 的消息要转成 `role="user"` 发给模型？ | 我们的协议是纯文本 JSON，不用 OpenAI 的 tool 消息格式。工具结果当成一条以 `Observation(工具名): ...` 开头的内容喂回去 |
| 压缩时为什么跳过 `visible=False` 的 assistant 消息？     | 那些是模型输出的原始 JSON 协议文本，塞进摘要毫无价值，只会占额度                                             |

### `agent/parser.py`（118 行）

| 追问                                         | 答法                                                 |
| ------------------------------------------ | -------------------------------------------------- |
| 为什么 `_MAX_OBJECT_SCAN=3`？                  | 一次输出里最多尝试解析 3 个 JSON 对象候选，避免在异常长文本上做无谓的全量扫描        |
| `action_input` 是字符串时为什么要再 `json.loads` 一次？ | 有些模型会把参数对象序列化成字符串塞进来，这是实测遇到的真实情况                   |
| `thought` 字段为什么允许为空？                       | 不能因为模型没写思考就判定失败，格式的硬要求只有 action 或 final_answer 二选一 |

### `tools/registry.py`（126 行）

| 追问                                   | 答法                                                                         |
| ------------------------------------ | -------------------------------------------------------------------------- |
| Schema 为什么不用 pydantic 生成？            | 手写 JSON Schema 足够，而且直接就是发给模型的格式，少一层转换。校验只做 required / type / enum 三项最小集，够用 |
| `invoke` 里为什么 `except Exception` 兜底？ | 工具内部任何 bug 都不能打断 Agent 循环。异常转成 `ok=False` 的结果回灌，模型有机会换工具                   |
| 未声明的额外参数为什么放行？                       | 模型偶尔会多塞字段。严格拒绝会导致本来能成功的调用失败，交给 handler 忽略更稳                                |

### `tools/calculator.py`（90 行）

| 追问            | 答法                                                                                                                     |
| ------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 为什么不用 `eval`？ | 安全。`eval("__import__('os').system('rm -rf /')")` 是经典 RCE。用 `ast.parse` 后遍历节点，只允许 `BinOp/UnaryOp/Constant` 和四则运算，其他一律拒绝 |
| 除零怎么处理？       | 捕获 `ZeroDivisionError` 转成 `ToolError`，回给模型的是可读错误而不是堆栈                                                                  |

### `session/store.py`（122 行）

| 追问                    | 答法                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------- |
| 两个窗口怎么保证不串？           | 每个窗口一个独立 `Session` 实例，消息列表和待办都在实例上。`SessionStore` 只是个 `dict[session_id, Session]`     |
| `asyncio.Lock` 加在哪一层？ | 加在 `Session` 上，`api.py` 里 `async with session.lock` 包住整个流式过程。同一会话并发请求会返回 409，不同会话互不阻塞 |

### `api.py`（94 行）

| 追问                             | 答法                                                                                                          |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| 为什么用 SSE 不用 WebSocket？         | 单向推送（服务端→前端），SSE 更轻，基于 HTTP 不用额外协议。前端用 `fetch + ReadableStream` 手写解析，因为 `EventSource` 只支持 GET，而 chat 是 POST |
| 为什么是步骤级流式而不是 token 级？          | 文本 JSON 协议必须拿到**完整输出**才能解析。token 级流式没法边解析边展示，与协议冲突。折中方案是：一旦产出一个 thought 或工具结果，立刻推                           |
| 流式里为什么还要 try/except？           | 响应头已经发出去了，中途异常没法再返回 500。必须转成 `error` 事件，否则前端会一直转圈                                                           |
| `X-Request-ID` 为什么自己生成而不是用中间件？ | 流式响应在中间件执行完之后才真正产出，中间件绑的 contextvar 会失效，所以在 `event_stream` 里显式重置                                            |

### `llm/client.py`（64 行）

| 追问                  | 答法                                             |
| ------------------- | ---------------------------------------------- |
| 为什么 5xx 重试、4xx 不重试？ | 5xx 是服务端抖动，重试有意义；4xx 是 Key 错、模型名错、参数错，重试一万次也一样 |
| 30 秒超时怎么定的？         | 大模型生成慢，太短会误杀；但也不能无限等，否则连接挂死。可配                 |

## 四、五个陷阱问题

### 「这些代码是你写的还是 AI 写的？」

**正面答**：「框架和模块划分是我定的，具体实现大量用了 AI 辅助。我能讲清每个文件为什么这样拆、每处取舍的原因，也改过 AI 给的版本——比如一开始 Calculator 用 `eval`，我换成了 `ast` 白名单；解析器最初的失败处理是直接抛异常，我改成了降级重试。」

**不要说**「都是我自己写的」。他一行行看代码，一定看得出。

### 「如果让你加第五个工具，需要改哪些文件？」

**答**：只加一个文件 `tools/xxx.py`，用 `@registry.tool(...)` 注册，再在 `tools/__init__.py` 里 import 一下触发注册。**运行时、解析器、前端都不用动**——这是注册机制的意义，Schema 会自动出现在 System Prompt 里。

（如果改成硬编码 if-else 分发，加工具就要改三处。这就是「注册机制」这个要求存在的理由。）

### 「模型一直调用同一个工具死循环怎么办？」

**答**：两道防线。硬防线是 `MAX_STEPS=5`，超了就兜底退出；软防线是 System Prompt 第 5 条明确「信息足够时立即回答，不要重复调用同一个工具」。还可以加「同一工具同一参数连续调用 N 次则拒绝」，但现在没必要。

### 「上下文压缩会丢信息，怎么办？」

**答**：会丢，这是取舍。缓解手段有三个：最近 8 条永不压缩、摘要只保留要点不做语义改写、原始消息不删除只标记游标（调试时可查）。升级方向是 LLM 增量摘要。

### 「你这个跟直接用 LangGraph 写有什么区别？」

**答**：功能上没区别，LangGraph 就是把这类循环抽象成图节点。区别在于我能说清它内部做了什么——它也是维护消息列表、调模型、解析输出、分发工具、判断是否继续。我写一遍才知道 `max_steps` 该设多少、工具结果该以什么形式回灌、解析失败该怎么兜。

## 五、答不上来时怎么办

绝对不要编。三种话术：

1. **知道大概，细节不确定**
   > 「这块我记得思路是按消息类型生成固定句子再截断，具体阈值我得看下代码。」（看代码不丢人，编造才致命）
2. **当时没想那么深**
   > 「当时这里我只考虑了能跑通，没深入。如果重做，我会考虑……」（承认 + 给出改进思路，能救回来）
3. **真是 AI 生成且你不知道**
   > 「这段是我让它生成的，我没吃透。我的理解是……」（然后讲你的理解，哪怕不完整）

面试官明确说了「务必理解 AI 写的代码」——他接受了 AI 辅助这个前提。**他的底线是你不装。**

## 八、现场演示脚本（3 分钟）

1. **打开** `backend/app/agent/runtime.py`，滚到 `run_turn`，讲「这就是题目要求的四步循环」（30 秒）
2. **跑一个带工具的**：「帮我查一下深圳的天气，然后记一个待办」→ 展开思考面板，指给他看 `weather → todo → answer` 三步（1 分钟）
3. **演示多窗口隔离**：新建会话，问「我有哪些待办」→ 空。切回窗口 1 → 有 1 条（40 秒）
4. **演示 max_steps**：可以说「你可以让它一直查天气，第 5 步会给兜底答复」（口头，不一定要跑）
5. **收尾**：打开 `parser.py` 讲降级链，这是最能体现「自己实现」的部分（40 秒）

## 九、最容易翻车的地方

1. **现场跑不起来**。提前在自己的机器上试一遍，注意 `cd backend` 和执行器的绝对路径。
2. **API Key 问题**。现场可能没网或没 Key，**一定用 `LLM_MOCK=1` 演示**，这样万无一失。
3. **被问到不存在的功能**。比如「你的向量检索怎么做的」——我们的 search 是词频匹配，直接说「用的是 2-gram 词频命中，没做向量，因为题目要求 mock 即可」。
4. **过度解释**。面试官问一句你答三分钟，容易被带跑。先给结论，他追问再展开。
